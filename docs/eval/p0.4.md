# Evaluation after P0.4: the refusal sentinel, and a thinking trial

P0.4 changed how a refusal is recognised. The prompt now tells the model to reply `NO_ANSWER_IN_CONTEXT` when the context doesn't hold the answer; a reply holding that token anywhere, or holding no text, is a refusal, and the user sees a fixed sentence. Before, a refusal was any answer containing "don't know". This file compares the run with [P0.5](p0.5.md) and the [P0.1 baseline](baseline.md) on the same 48 frozen questions, then reports a trial of the model's lowest thinking level.

### The one change: v2-paraphrase-01, facts

"will my data be shared?" is answerable from Art. 15, and the model judges the context doesn't answer it, in both runs. In P0.5 it replied "I don't know. The provided context does not contain information about whether your personal data will be shared…" and went on to explain Art. 15; the explanation held the expected facts, so the refusal scored as having them. Now it replies with the bare sentinel, the user sees the fixed sentence, and the facts are gone. Refusal was wrong in both runs, and the tier BRONZE (expected GOLD). The model's judgement didn't change; the explanation that carried the facts did.

### How the model used the sentinel

41 questions reached the model. Every refusal was the token alone:

| Reply | Questions |
|---|---|
| exactly `NO_ANSWER_IN_CONTEXT` | 14 |
| the token with other text around it | 0 |
| a refusal in words, without the token | 0 |

In P0.5, 4 of the 14 model refusals had text around "I don't know" (3 an explanation after it, 1 a preamble before it). Given an explicit instruction, the model complied every time in this run, so matching the token anywhere rather than alone made no difference here. It stays the safer rule: one stray preamble would otherwise show the token to a user, possibly as GOLD. Counted from the raw replies in the eval's cache (`evals/cache/`, gitignored), with no "don't know", "does not contain", "not mention" or similar phrase in any answer.

## The thinking trial: the rule, written before the run

Gemini models "think" before answering; less thinking is faster, and may be worse. The trial runs the same 48 questions with the lowest thinking level the model accepts (MINIMAL, the lowest in the installed `google-genai`; LOW if the API refuses MINIMAL), against run 1 (`p0.4`, the model's default thinking). This rule was fixed before the trial ran:

Keep the lower thinking level only if, against run 1, all three hold:

1. **Every out-of-corpus question that run 1 refused is still refused.** Answering a question the corpus can't answer is the failure that matters most.
2. **Refusal, facts and tier overall each lose at most one question.** One question is the smallest change the set can show, and run-to-run variation at the same settings hasn't been measured.
3. **The median model call is at least 25% faster.** Below that, the saving isn't worth a change in behaviour.

Sources can't change: they depend on retrieval alone. If any condition fails, the default thinking stays.

**Against the rule, every condition held:** all 14 out-of-corpus questions refused, as in run 1; refusal and facts each lost one question and tier gained two; the median call was 55% faster. By the rule, MINIMAL would be kept.

**Question by question, three changed:**
- **v2-paraphrase-01** ("will my data be shared?"): answered from Art. 15 at MINIMAL, where run 1 refused it. Refusal, facts and tier all fixed (GOLD).
- **v2-conflict-01** ("what is our deadline for reporting a personal data breach?"): refused at MINIMAL, although four Art. 33 chunks passed (best 0.743) with the retention policy's breach section. Run 1 answered with both deadlines, 72 hours to the authority and 30 days to the DPO. The refusal made the tier BRONZE, which matches the label for an unrelated reason (the label expects the draft's breach section to veto the answer; that section doesn't pass the filter). So one of the two tier gains is a coincidence, not a fix.
- **v2-conflict-03** ("what is the deadline for answering a subject access request?"): refused at MINIMAL; run 1 gave each document's deadline.

**A repeat check, to tell an effect from noise.** The model samples at its default temperature, so one run can't say whether a refusal is systematic. The two newly refused questions and the demo's own breach question were each asked five more times at each setting, with the same prompt and chunks, outside the eval cache:

| Question | Default | MINIMAL |
|---|---|---|
| "what is our deadline for reporting a personal data breach?" | answered 5/5 | refused 5/5 |
| "what is the deadline for answering a subject access request?" | answered 5/5 | refused 4/5 |
| "How long do we have to report a data breach?" (the demo's wording) | answered 5/5 | answered 5/5 |

At MINIMAL the model systematically refuses questions whose sources disagree, where default thinking answers by setting out each document's deadline.

**Decision: default thinking stays, overriding the rule.** The rule was met, but it counted questions overall and didn't anticipate losses concentrated in one group. Here they fall on the conflict questions, which Phase 2 (comparing a policy's deadline with the regulation's) is built on, and the repeat check shows they are systematic. A reviewer asking "what is our deadline…" would get no answer while Phase 2's gap card showed the conflict beside it. Raj made the override after seeing the repeat check, and it is recorded here and in the decision log. The cost: answers keep taking about 3.3 s at the median (5.4 s at the slowest) instead of 1.5 s. Both runs' results stay committed.

**The lesson for the next rule:** a keep rule should also protect each group, not only the totals.
